# 8ブログ共通のBlogger運用Runbook

## 目的と適用範囲

この文書は、8ブログ共通で行う下書き保存、既存下書きの完全保存、画像1枚の追加、予約投稿、公開後監査の実行手順である。記事の内容判断、Bloggerでの手動公開、OpenAI API利用、画像生成は対象外とする。

下書き保存と予約投稿は別の変更境界である。どちらの操作でも、対象ブログ・投稿ID・ローカル正本を照合できない場合は停止する。別の記事や別ブログを推測で選ばない。

## 共通の事前条件

すべての変更操作で、次を満たす。

- ローカルの品質監査済みパッケージに、タイトル、本文、公式情報リンク、ラベル、検索説明、slug、画像方針がある。
- 対象ブログの `blogKey`、Blogger blog ID、投稿ID（既存下書きの場合）が実行パッケージと一致する。
- 対象投稿は下書きであり、公開済みでも予約済みでもない。ただし予約設定の操作では、予約前の下書き状態を確認する。
- `data/STOP` が存在しない。各UI変更の直前にも停止状態を再確認する。
- 下書き操作では `ENABLE_DRAFT_SAVE=true` かつ `ENABLE_SCHEDULED_POST=false`、予約操作では `ENABLE_DRAFT_SAVE=false` かつ `ENABLE_SCHEDULED_POST=true` を使う。両方を有効にしない。
- 変更対象のブログIDは明示的な許可リストに含まれる。

対象外投稿、同名投稿の重複、認証切れ、Blogger編集画面のブログ不一致、UI要素未検出、保存完了表示未検出はすべて停止条件である。停止後は追加の変更をせず、スクリーンショット・HTML・ジョブ成果物を残して読み取り監査へ進む。

## 1. 新規下書きの保存

### 実行経路

`DraftSaveService.execute` → `BloggerDryRunClient.saveDraft` を使う。

1. 同一タイトルの既存下書きを読み取り、0件だけを許可する。
2. セッションとBlogger編集画面のブログIDを確認する。
3. タイトルとHTML本文を入力し、タイトルを読み戻す。
4. ラベル、検索説明、カスタムパーマリンクを設定して各入力値を読み戻す。
5. 画像がある場合はCompose表示へ切り替え、画像を挿入する。画像挿入後はラベルが未確定になり得るため、メタデータを再適用する。
6. 「その他のオプション」→「保存」を優先し、無い場合だけ通常の保存ボタンを使う。保存完了表示と編集URLを記録する。

### 成功判定

コード内の成功は、保存完了表示、保存後の編集URL、証跡ファイルの生成までである。運用上の成功は、**新しいブラウザコンテキスト**で再読込して、下書き状態、タイトル、本文、公式情報リンク、ラベル、検索説明、パーマリンク、画像1枚、予約なしをローカル正本と照合して初めて確定する。

### 停止と再試行

同名投稿が1件以上ある場合は新規作成をしない。認証・ブログID・保存表示・編集URLのどれかが失敗した場合も再試行しない。投稿一覧と成果物を読み取り、投稿IDが特定でき、下書きであることを確認した上で、既存下書きの完全保存として別途承認する。

## 2. 既存下書きの完全保存

既存下書きの更新は `postEditorUrl` と `ENABLE_EXISTING_DRAFT_UPDATE=true` が必要である。投稿ID、ブログキー、現タイトル、下書き状態、予約なし、公開なしを読み取り照合してから、新規下書き保存と同じ本文・設定・画像の経路を使う。

保存後は新しいブラウザコンテキストで正本との差分監査を行う。タイトル、本文、公式リンク、ラベル、検索説明、パーマリンク、画像数、下書き状態、予約日時を項目ごとに記録する。いずれかが不一致なら失敗とし、本文へ空白を追加・削除するような保存の強制は行わない。

### 再利用可能な完全監査CLI

保存後の監査には、変更操作を持たない次のCLIを使う。

```powershell
node dist/cli/index.js audit-existing-draft `
  --blog <blog.json> `
  --article <audited-article.json> `
  --post-id <Blogger-post-ID> `
  --editor-url <exact-Blogger-edit-URL> `
  --output <new-audit-report.json>
```

このコマンドは、対象編集URLを新しいブラウザコンテキストで再読込し、別の新しいコンテキストで同一タイトルの投稿一覧を読む。Bloggerへクリック、入力、保存、公開、予約、削除は行わない。レポートには対象投稿ID、各項目のPASS/FAIL、期待値・実測値、理由、実行時刻を出力する。

CLIが確認するのは、ブログID、投稿ID、編集URL、下書き状態、予約なし、公開なし、タイトル、本文、本文中のHTTPSリンク、ラベル、検索説明、パーマリンク、画像数、同一タイトルの重複である。編集画面または投稿一覧を読めない場合は `UNVERIFIED`、読み取った投稿状態が不明または同名投稿が複数ある場合はFAILとして扱い、修復は実行しない。

### 8ブログ向けバッチ完全監査

複数記事の監査には、記事ごとのブログ設定パス、正本パス、投稿ID、編集URL、slugを持つ [バッチマニフェスト例](../examples/existing-draft-audit-batch.example.json) を使用する。

```powershell
node dist/cli/index.js audit-existing-draft-batch `
  --manifest <audit-batch.json> `
  --output <new-empty-output-directory>
```

マニフェストは、投稿IDと編集URLの重複を許可しない。CLIは全ブログ設定・正本を読み取った後に、slugと正本、編集URLと投稿ID、編集URLとブログ設定の対応を事前検証する。この事前検証がFAILならBloggerを開かず、出力ディレクトリも作らない。

検証を通過した場合、各記事は順番に新しいブラウザコンテキストで監査する。1件の監査FAILまたは `UNVERIFIED` は残りの記事を止めず、`01-<slug>.json` の記事別レポートと `summary.json` の集計レポートへ別々に集計する。`--output` は存在しない新規ディレクトリだけを受け付け、既存の監査証跡を上書きしない。

## 3. 既存下書きへの画像1枚追加

画像専用更新は `DraftSaveService.executeImageOnly` → `BloggerDryRunClient.updateExistingDraftImage` を使う。本文・タイトル・ラベル・検索説明・パーマリンクは変更しない。

1. 正確な編集URL、下書き状態、タイトル、既存画像数0を確認する。
2. 「画像を挿入」→「パソコンからアップロード」を**クリック**してGoogle Pickerまたはネイティブ選択を開く。EnterキーだけでPickerを開こうとしない。
3. ネイティブfile chooser、Picker iframe内のfile input、Pickerの参照ボタンの順に画像を検出する。検出できない場合は変更せず停止する。
4. 挿入後にレイアウト確認が出た場合は確定し、本文内の画像数が1になるまで待つ。
5. 「その他のオプション」→「保存」で保存し、同じ編集URLを再読込して画像数が1であることを確認する。

このコード内の再読込は同じブラウザコンテキストであり、確認項目もタイトルと画像数が中心である。したがって運用完了には、新しいブラウザコンテキストで本文と全設定の不変性を照合する外部監査が必要である。画像が既に1枚以上、二重挿入、Picker未検出、保存後の画像数が1以外なら停止し、自動再試行しない。

## 4. ラベル・検索説明・パーマリンク

ラベルはBloggerのオートコンプリート入力である。通常のキーボード入力後にTabでフォーカスを外し、入力値を確認して確定させる。検索説明とカスタムパーマリンクも入力後に読み戻す。slugは小文字ASCII英数字とハイフンのみ、検索説明は150文字以下、ラベルは各200文字以下である。

保存後の別コンテキスト監査で、ラベル集合、検索説明、カスタムパーマリンクを正本と比較する。Bloggerの公開フィードから検索説明・ラベル・編集用パーマリンクを完全には検証できないため、これらは編集画面で確認する。

## 5. 予約投稿

予約投稿は、下書き保存とは独立した承認済み実行パッケージに限る。次の順序を崩さない。

```text
schedule plan
→ approval
→ readiness
→ non-mutating browser preview
→ preview confirmation
→ execution package
→ package audit
→ explicit execution confirmation
→ scheduled execution
```

実行直前に投稿ID、ブログキー、下書き状態、本文、公式情報リンク、ラベル、検索説明、パーマリンク、画像1枚、Asia/Tokyo設定、予約日時衝突を照合する。公開ボタンと確認ボタンを通った後は、予定日時のJST表示・予約状態・内容を読み取り監査する。

日時の10分以内、時刻/タイムゾーン不一致、証跡ハッシュ不一致、重複予約、対象外ブログ、予約済み・公開済み投稿は停止条件である。予約操作の再試行は、同一の承認済み証跡と投稿IDについて、既存の境界が許す場合だけ別途承認して行う。手動公開はしない。

## 6. 公開後監査

予約時刻の30分後以降、未監査の記事だけを読み取り専用で確認する。

- Blogger上の公開済み状態、公開日時（JST）、投稿ID、公開URL
- タイトル、本文、公式情報リンク、画像1枚
- ラベル、検索説明、パーマリンク
- 公開ページの表示、同一タイトルまたは投稿IDの重複公開

`PublishedPostAuditService` が自動確認するのは、公開フィードの同一タイトル1件、非空本文、HTTPSの公開URL、Blogger管理ホストの画像1枚、画像HTTP応答である。ラベル、検索説明、編集用パーマリンク、公開ページの見た目、本文が正本と完全一致することは、このサービス単独の保証範囲外である。これらはBlogger編集画面、公開URL、ローカル正本を用いる監視レポートで確認する。

単一記事で公開ページと編集画面を正本へ照合する場合は、次の完全監査を使う。

```powershell
node dist/cli/index.js audit-published-post-complete `
  --blog <blog.json> `
  --article <audited-article.json> `
  --post-id <Blogger-post-ID> `
  --editor-url <exact-Blogger-edit-URL> `
  --output <new-audit-report.json>
```

複数の公開予定記事は `audit-publication-monitors --manifest <monitor-batch.json> --output <new-directory>` で監査する。予定時刻から30分未満の `PENDING` は変更せず、期限到達後だけ完全監査を行う。一時的な読取エラーは最大3回に制限し、確認不能はFAILではなく `UNVERIFIED` として残す。`UNVERIFIED` の再監査は `--retry-unverified true` を明示した場合だけ許可する。既存のPASS/FAILは再実行しない。

公開失敗、日時不一致、表示崩れ、画像・公式リンク欠落、重複公開は記事単位でFAILとし、再公開・再予約・削除を自動実行しない。日別レポートとバッチ集計レポートに証跡と理由を保存する。

## 7. 監査対象選定と予約パーマリンク監査

ローカル正本候補から既存下書きの監査対象を準備する場合は、`prepare-existing-draft-audit-selection` で重複・欠落・矛盾を先に除外し、`select-existing-draft-audit-targets` で投稿一覧と新しい編集コンテキストを読み取る。出力が空でも有効な選定レポートを残し、投稿ID・ブログID・編集URL・タイトル・状態を推測しない。選定後の完全監査は `audit-existing-draft-batch` へ明示的に渡す。

予約投稿のパーマリンク状態は次の3段階に分ける。

```text
audit-scheduled-permalinks
→ reaudit-scheduled-permalink-unverified
→ prepare-scheduled-permalink-repair
```

最初の監査は、投稿ID、編集URL、ローカル正本、予約状態、JST日時、本文と設定を照合し、パーマリンクを `MATCH`、`EMPTY`、`DIFFERENT`、`UNVERIFIED` に分類する。再監査は前回 `UNVERIFIED` の投稿だけを対象にする。修復準備は、パーマリンクが空で、それ以外の全監査項目がPASSの投稿だけを `PERMALINK_ONLY` 候補に含める。本文や設定にも差分がある投稿と接続不能な投稿は除外する。

再監査では、前回レポートにない投稿を追加せず、batch、blogKey、slug、投稿ID、編集URL、予定日時が前回の `UNVERIFIED` 項目と完全一致する場合だけ置き換える。空ではなく別値のパーマリンクは `CANONICAL_DIFFERENCE` であり、`PERMALINK_ONLY` 修復候補にしない。修復準備では、監査項目と候補分類の欠落・重複・改変、および必須監査チェックの欠落を出力作成前に拒否する。

これら3コマンドはBloggerを読み取るかローカルJSONを作るだけで、修復を実行しない。生成されるapproval-only packageも実行権限ではない。実際の保存、予約解除、再予約には、対象を固定した別のgoal、最新の事前監査、専用フラグ・許可リスト・STOP確認、ユーザーの明示承認が必要である。

## 現在の非対応範囲

- 未入力のブログ、投稿ID、編集URL、ローカル正本を自動推測して対象にしない。
- 監視コマンドを常駐実行、無人再試行、または自動修復しない。
- 読取不能を成功や内容不一致へ変換せず `UNVERIFIED` で停止する。
- 監査・修復準備から保存、予約、公開、削除へ自動遷移しない。
- Blogger UI変更、ログイン切れ、OSファイル選択画面を自動回避しない。
- 一回限りのcanaryスクリプトは一般的な修復コマンドではなく、新しい承認なしに再利用しない。

## 実装との対応と既知のUI依存

| 操作       | 実装上の確認                                                 | 運用で追加する確認                                                       | UI依存・手動判断                                     |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------------------ | ---------------------------------------------------- |
| 新規下書き | 許可リスト、重複検出、セッション/ブログID、保存表示、編集URL | 新コンテキストで全項目の正本照合                                         | Bloggerの保存表示とメニュー配置                      |
| 完全保存   | 既存編集URL、下書き状態、タイトル入力、保存経路              | 単記事は `audit-existing-draft`、複数記事は `audit-existing-draft-batch` | 編集画面の状態表示                                   |
| 画像追加   | Picker直接クリック、画像1枚、保存後の同一コンテキスト再読込  | 新コンテキストで本文・設定・画像の一貫性                                 | Picker iframe/file chooser、画像レイアウトダイアログ |
| 予約投稿   | 承認・ハッシュ・時刻・タイムゾーン・確認ダイアログ           | Blogger上の予約状態とJST表示                                             | Publish確認UI、ブログ設定                            |
| 公開後     | フィード上の公開URL・本文・画像1枚                           | メタデータ、表示、正本一致、重複                                         | 公開反映の遅延、Blogger画面と公開ページ              |
| 監査選定   | ローカル証跡、投稿一覧、編集URL、状態、重複                  | 選定後の完全監査                                                         | 投稿一覧と編集画面の現在UI                           |
| 修復準備   | パーマリンク以外がPASSの候補だけを分類                       | 別goalでの承認・最新preflight・保存後監査                                | 予約解除・保存・再予約の現在UI                       |

PickerがOSのファイル選択画面を開き、コード側でfile inputを検出できない場合は、操作を停止してユーザーのファイル選択を待つ。手動選択後も、画像挿入・保存・再読込・全項目監査はこのRunbookの成功判定に従う。

## 証跡の保持

ジョブ成果物、スクリーンショット、HTML診断、実行パッケージ、ハッシュ監査、保存後の差分監査、公開後の日別・集計レポートを同じバッチ単位で保持する。sealed JSONや既存の実行証跡を上書き編集しない。
